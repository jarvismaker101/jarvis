## Fixed: model sidebar — no model could be selected for any feature

**Symptom.** In the model sidebar (hamburger), no feature's model options could be
selected. The chat/TTS/STT/vision/browser-tool sections showed no models, so
`/settings/model` was never called.

**Root cause.** `frontend/renderer.js` — `jarvisFetch()` called ITSELF instead of
delegating to the platform fetch:

```js
function jarvisFetch(url, opts) { ... return jarvisFetch(url, opts); }   // infinite recursion
```

Introduced during the G11/F51 sandboxed-renderer refactor, where the old
`fetch(...)` call was swapped for the wrapper's own name. Every call threw
`RangeError: Maximum call stack size exceeded`, so `loadProviders()`
(`GET /settings`) and `_loadProviderModelsForRole()`
(`GET /providers/{id}/models`) both failed, and the sidebar rendered
"could not load settings". This also silently broke `/ask/stream`,
`/settings/model`, `/settings/provider`, `/ui-state` and `/speak/stop`.

**Fix.** `jarvisFetch` now awaits the preload bridge once (so the port + token
are resolved before the first request), attaches `X-Jarvis-Token` (the trusted
chat window is the only renderer that can obtain it), and delegates to native
`fetch` — required because `/ask/stream` needs a real streaming body that the
buffered IPC proxy cannot provide. A renderer without `fetch` falls back to the
policy-gated `IPC.backend` proxy, wrapped into a Response-like object.

## Reusable technique

`frontend/*.js` are plain browser scripts (not modules) loaded in a
`contextIsolation` + `sandbox` renderer, so they cannot be `require`d. To test
them headlessly: run the source in a `vm` context over a small DOM stub
(className/classList/children/querySelector-by-class/appendChild) and stub
`fetch` + `window.jarvisAPI`. Note that top-level `let`/`const` are NOT exposed
on the sandbox object — only function declarations are, so drive the code
through its functions and read results from the DOM stub. Use inert
`setTimeout`/`setInterval` in the sandbox or the renderer's UI polling loops
will hold the test process open.

## Reusable technique — polished reportlab PDFs (non-obvious pitfalls)

Generator kept at `%TEMP%\jarvis_audit\build_report.py`. Six traps that all
produced silently-wrong output:

1. **Escape order.** `esc()` must decode named HTML entities (`&mdash;`
   `&quot;` `&amp;` `&rarr;` `&asymp;` `&middot;` `&nbsp;` `&lt;` `&gt;`) to real
   characters **before** escaping `&`/`<`/`>` — otherwise `&` → `&amp;` first
   and `&mdash;` renders literally as `&mdash;`. Put `&amp;` last in the decode
   table so double-encoded text degrades correctly.
2. **Inline markup allow-list.** `esc()` should stash an allow-list
   (`</?(?:b|i|u|font|br)\b[^<>]*/?>`) behind placeholders, escape, then
   restore — so narrative strings can author `<b>` while every other `<` stays
   literal. Sentinel-based (`[[b]]`) content and direct `Paragraph("<b>…")`
   markup both keep working.
3. **Unicode glyph coverage.** Base-14 Helvetica/Courier silently drop
   `→ ≈` etc. Fix: `pdfmetrics.registerFont(TTFont("Helvetica",
   "C:/Windows/Fonts/arial.ttf"))` (+ Bold/Oblique/BoldOblique, and
   `Courier`→`cour.ttf`). Arial is metrically identical to Helvetica and
   Courier New to Courier, so **layout is unchanged** and every existing style
   picks it up with no edits.
4. **Table column widths** must fit the longest *unbreakable* word —
   "IMPLEMENTED" at 8.2 pt bold needs ≥ 26 mm or it wraps to "IMPLEMENTE / D".
5. **Orphan pages.** A summary paragraph after a long paginated table lands
   alone on a new page; move lead-in summaries *before* the table.
6. **Verify by rasterising, not just extracting.** `pypdf` text extraction
   reflects the ToUnicode map, so a missing glyph can still extract correctly.
   Render pages with `pymupdf` (`page.get_pixmap(dpi=105).save(...)`) and
   actually look at them. Installed `pymupdf` into the managed venv for this.

## Fixed: total silence — `PortAudioError: Stream is stopped [-9983]`

**Symptom.** Jarvis produced NO audio at all, on every engine (Fish *and* the
new Google fallback). The user's traceback ended in
`fish_voice._do_pcm_stream` -> `_play_pcm_through_actor` -> `actor_play` ->
`stream.write` -> `sounddevice._raw_write` -> `PortAudioError: Stream is
stopped [PaErrorCode -9983]`.

**Root cause.** `backend/services/audio_actor.py` (the F32 single playback
owner) opened its `sd.OutputStream` but never called `.start()`.
**`sd.OutputStream` opens a blocking stream in the STOPPED state**; sounddevice
only ever calls `start()` from its own `with` statement (`sounddevice.py`
~line 1111 `__enter__`), never from `__init__`. `Pa_WriteStream` therefore
rejects the FIRST write with `paStreamIsStopped` (-9983) — so every utterance
died on its first chunk, whatever engine produced the PCM.

**Diagnosis path (worth repeating).** Reproduced deterministically with a plain
sequential `_play_pcm_through_actor()` call (not a race). Probed every output
device x all four host APIs (MME/DirectSound/WASAPI/WDM-KS) x 44100/48000 x
mono/stereo — ALL failed with -9983. Devices 24-43 failed with a *different*
error ("Unanticipated host error"), which pointed at the sandbox. Crucially
`sd.play()` + `sd.wait()` **succeeded**, proving the machine *does* play audio
and it was not a sandbox restriction. Isolating the variable: `blocksize`
(4096 vs 0) was irrelevant; only an explicit `start()` fixed it.

**Fix.** `audio_actor.py`:
- `SoundDeviceStream.__init__` -> `self._stream.start()` after construction.
- `make_sounddevice_factory._factory()` -> `stream.start()` before wrapping in
  `RawPcmStream`.
- `AudioActor.play()` write is now guarded so a stop landing between the
  generation check and the write (barge-in) ends the utterance quietly instead
  of reporting a PortAudio error for a stop the user asked for.

**Verified on real hardware:** `PLAYED ok=True bytes=35280 in 1.42s` (and a
longer run: 217972 bytes in 3.41s). No more -9983.

**Why the whole suite was blind to it.** The old test fake tolerated a missing
`start()` — the entire suite passed green while the app produced no audio.
Added `PortAudioContractStream` in `backend/tests/test_f32_playback_owner.py`:
a fake that raises `RuntimeError("Stream is stopped [PaErrorCode -9983]")` on
any write before `start()`, plus `StreamStartContractTests` (4 tests) covering
the default stream, the format factory, device release, and the abort race.
21 tests in that file now pass. Lesson: **a test double that does not enforce
the real device's contract can hide a total-failure bug.**

Assertions check `start_calls > 0`, NOT the `started` flag — `play()`'s
`finally` calls `stop()`, which legitimately clears `started`.

**Suite status:** backend 2122 pass / 1 pre-existing order-dependent failure
(`test_f02_goal_routing::test_a_proposal_status_is_proposal_not_needs_input`,
passes in isolation); JS 28/28 pass. The 2 `test_browser_agent` failures seen on
the first (cold, 88s) run were timing flakiness under load — they pass in the
67s runs and in isolation.

**Requires a relaunch** via `run_jarvis.bat` — `.env` is read at import and the
watcher spawns uvicorn without `--reload`, so a running Jarvis keeps the old
code.

## Google TTS: 1.5x speed-up (pitch-preserving)

**Reported:** "google tts sounds like its in slow motion so speed it up by
1.5x".

**Diagnosis first — the decode was NOT the bug.** Measured it: the endpoint
returns **24 kHz** MP3, and `fish_voice._decode_audio` resamples with PyAV's
`AudioResampler(rate=44100)`, so a 5.208 s clip decodes to 5.207 s of PCM.
Duration is preserved exactly and the stream is opened at 44100, so nothing
was being played back at the wrong rate. Google's `tw-ob` voice is simply
drawly next to Fish — the request was legitimate, not a defect.

**Fix:** time-stretch the decoded PCM with ffmpeg's `atempo` via PyAV's filter
graph, in the new `google_tts._speed_up()`. **Deliberately NOT a resample** —
a resample is two lines but moves a 440 Hz tone to 660 Hz, i.e. a chipmunk.
`atempo` is a WSOLA time-stretch, so the voice keeps its pitch.

Details worth remembering:
- PyAV filter graph: `abuffer` → `atempo` → `abuffersink`, then push
  `av.AudioFrame.from_ndarray(block.reshape(1, -1), format="s16",
  layout="mono")` per 1 s block and pull until it raises; `push(None)` flushes.
  `graph.add_buffer(template=<stream>)` does NOT work — it wants a *frame*
  (`AttributeError: 'AudioCodecConfig' object has no attribute 'width'`).
- `DEFAULT_SPEED = 1.5`, clamped to 0.5-2.0 (atempo's per-instance range),
  overridable with `JARVIS_GOOGLE_TTS_SPEED`; 1.0 skips the filter entirely.
- Speed is resolved **once** per utterance and threaded through both the
  stretch and the cache key, so they cannot disagree. The cache key's format
  slot is now `pcm@1.50x` — without it, changing the tempo would replay the
  old cached take.
- Any failure returns the untouched PCM, so a broken filter degrades to
  normal-speed speech, never silence.

**A test caught a real bug:** `float("nan")` parsed fine and then survived
`min()/max()` comparisons, clamping to the 2.0 ceiling instead of falling back
to the default. Fixed with `math.isfinite()` — NaN/inf are typos, not an
intent to max out.

**Verified:** 2.0 s sine → 1.5x gives ratio 1.498 with the FFT peak still at
440 Hz; `_decode_pcm` applies it; end-to-end `speak_google_tts` returned True
with 2.883 s of audio (was ~4.3 s). Suite: **2131 passed** (8 new tempo tests),
1 pre-existing failure, `.env` MD5 unchanged, recycle count still 18.
